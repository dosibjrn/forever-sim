**Owner-approved v2.21 (2026-11-04): native source of optimizer alternatives.** The exact-SHA-pinned MythicSim Rust fork is the one Warcraft data/legality owner. Its embedded item/enchant/spell tables, talent layouts and prepared spellbook/APL machinery are the basis for available gear, enchant, talent rank and executable APL action/condition choices. **These existing data do not constitute an already implemented native options-enumeration API or complete legality coverage.** For active P7.5 and generic gear × talents × APL optimization, extend the maintained Rust fork only where a real production caller needs missing legal choices/capabilities; pin the tested revision. Forever asks Rust for available alternatives, proposes/mutates/crosses them, passes the complete request back to the selected native prepare/validate/simulate path and scores actual results. No permanent Python/SQLite source inventory, GameIR, copied eligibility tables, Druid-specific talent checker or duplicate game mechanics. Delete retired P1/P2-only pipelines outright; migrate true active consumers before retiring their transitional code. Retain the approved Go execution alternative and all existing native↔world obligations where applicable. **This changes ownership and implementation, not P3–P7.5 acceptance, 148/1332 scope, 30/300-second cold-search windows, native-world causality, 100-mob runs, balanced-RNG candidate scoring or the frozen 1,000-stochastic final. No new gate, extra validation round, preflight proof or automatic PASS/FAIL is created.**

**Owner-approved v2.14 (2026-11-02): P7 validation and RNG.** P7.1–P7.5 internal independent cold searches evaluate actual source-legal configurations with deterministic **balanced RNG and few repetitions** for efficient, comparable optimization; they do not use expensive stochastic acceptance loops to rank candidates. The original saved request's iteration count is provenance, not a requirement to replay 10k. This overrides older P7-specific threshold/iteration language; P7 source legality, fixed reference config, native↔world causality, independent 300 s searches and the then-current 148×11 acceptance scope remained unchanged at that time; v2.20 later retired P1/P2. See [P7](docs/gates/P7.md).

## Authority and change control

- Explicit owner instructions take precedence. Approved PROCESS governs implementation/acceptance; approved OVERALL PLAN governs product goals; [WORK_PRIORITY](docs/planning/WORK_PRIORITY.md), issues and work plans may be freely reprioritized within those constraints.
- **Only an explicit owner instruction/approval may substantively change PROCESS, its linked gate criteria, or OVERALL PLAN.** Update canonical files via reviewed Git commits; rely on Git history, not numbered sibling documents or repeated approval logs.
- Any conflicting lower-level instructions lose. Do not silently change acceptance thresholds, source legality, backend rules, or the 148-checkpoint scope.
- **P7 authority:** active P7 acceptance is defined by [P7.1–P7.5](docs/gates/P7.md). The v7 Overall Plan's old-optimizer challenger is a separate P4–P6 comparison requirement, not a replacement P7 gate.

## Native candidate-source and execution workflow

1. **Read native options, do not copy game facts.** For a concrete class, level, spec, encounter/scenario and current candidate, obtain relevant gear/slot/item/enchant alternatives, talent rank/build possibilities, executable APL spells/actions/conditions and structured refusals from the pinned MythicSim Rust authority. The existing Rust tables/preparation are not proof that such a complete query already exists. Add the *minimum needed* Rust-owned API/capability for an active production consumer where missing, rather than reconstructing an inventory in Python.
2. **Search remains in Forever.** The shared class-neutral search generates independent cold candidates and mutates/recombines multiple axes; keep scheduling, paid score comparison, exploration and frozen winner selection in Forever. An options response defines available proposals, **not** a PASS, an accepted build or a substitute for a genuinely paid simulator run.
3. **Rust decides the whole build.** Submit each proposed whole candidate to the selected real native prepare/validate/execute path. Honor its valid, invalid and unsupported outcomes without duplicating restrictions or silently filtering possible actions with a Python class whitelist. Use the native↔2D/world execution and stochastic/balanced RNG paths already required by the particular active gate. Preserve any approved Go execution path during migration.
4. **Replace only necessary live dependencies.** Prioritize failing active P3–P7.5 and actual optimizer callers; preserve working behavior until the native replacement executes, then delete displaced Python GameIR, SQLite/rule catalogues and class-specific validators. Retired P1/P2 diagnostics and dead routes need deletion rather than new native counterparts. These changes are implementation work, **not an extra gate**, and do not demand re-running unaffected accepted tests.

## Acceptance contract

- The scoreboard has **148 checkpoints**: nine unrestricted classes × four levels (20, 30, 40, 60) = 36; Druid four profiles × four levels = 16; eight other classes × three profiles × four levels = 96. There is no L50 checkpoint.
- A checkpoint counts only when **P3–P6 and P7.1–P7.5** have each genuinely passed with mutually compatible source, ruleset and production-engine semantics. Acceptance can accumulate across separate runs; all gates need not pass in a single session or be rerun merely because unrelated commits landed. P3–P6 assess continuous **100-mob leveling**; P7 assesses a separate pinned MythicSim DPS-reference encounter. Never splice incompatible proofs.
- **No additional implicit gates.** Tests, metadata, compilation, static manifests, native-only diagnostics, partial evidence and green CI are not a substitute for the actual stated predicate. Report PASS/FAIL/BLOCKED truthfully. Preserve previously accepted owner-specific historical decisions and disclose their limits.
- Exact requirements and runtime authority:
  - [Common acceptance, engines, sources and transition](docs/gates/COMMON.md)
  - **Retired:** P1/P2 have no active acceptance contract, CLI entry point or M1 record; earlier criteria are historical only.
  - [P3 gear smoke](docs/gates/P3.md)
  - [P4–P6 independent search and 100-mob comparison](docs/gates/P4-P6.md)
  - [P7.1–P7.5 MythicSim reference and live integration](docs/gates/P7.md)
- Stable on-demand CLI: `python tools/wf_gate.py --class <class> --level <level> --gate P3` (or P4–P7.5). Actual production execution, not prewritten JSON, awards a new PASS; see [runtime contract](docs/gates/RUNTIME_AUTHORITY.md). Acceptance tests may be CLI/integration runs and need not be pytest unit tests.

## Delivery and evidence

1. Prioritize the smallest **material critical-path improvement** toward 148/148, not documents, run counts, checklists or status theater. Use the mutable work priority and actionable issues; parallelize independent code work.
2. Develop in an isolated branch. For a new/repaired gate, show **RED → GREEN → REFACTOR** against the *same* behavioral predicate; refactor shared mechanisms rather than implementing per-class exceptions, then rerun relevant cross-class/level regressions.
3. A passing **formal gate** requires **one real run** of the selected production code against the applicable approved gate predicate: source/ruleset/engine, inputs, measured effects, searches, comparisons and world causality are genuinely used where the gate requires them. The **persistent acceptance record may be only a gate-specific `PASS` and its timestamp**; optional run/commit links aid debugging but committed JSON, a `docs/evidence/` bundle, or a separate proof implementation is **not** mandatory. The test/production implementation remains executable for later revalidation. A timestamp cannot manufacture a PASS without the real successful run. Never mix incompatible runs or raise 0/148 on partial proof.
4. **Run once, retain PASS, revalidate only when materially invalidated.** Do not routinely repeat heavy 30s/300s/100-mob/holdout acceptance runs each hour, commit, PR or CI cycle; a different git SHA alone is not invalidation. If a changed source rule, affected production behavior, chosen engine, scenario or scoring semantics defeats the earlier test's relevance, rerun only the affected gate(s) and update their PASS timestamp upon success. Safe engineering changes may merge after appropriate **fast** regression tests without changing unrelated accepted gates. Record actionable failures, not reporting bureaucracy.
5. Use sourced Forever data and justified Classic defaults where Forever is unknown. Implement and test observable mechanics; don't require live-server measurement or speculative semantic-certification rounds. No invented game values, no hidden source completeness gates; see [common source rules](docs/gates/COMMON.md).
