- **Raportoi täsmällisesti:** mikä on *todistettu*, mikä on *vielä testaamatta*, mikä on *seuraava oikea gate-vaatimus*. Älä listaa todentamattomia mahdollisuuksia “seuraavina teknisinä esteinä”. Näytön puuttuessa jatka toteutusta tai ilmoita yksinkertaisesti, ettei testiä ole vielä ajettu.

## Operating model

- **Five independent conversations, five independent hourly tasks:** Prio XX:00; Work1 XX:10; Work2 XX:20; Merge XX:40; Clean XX:50, timezone Europe/Helsinki. Each task is created in its **own conversation**, never all five in one transcript. These times are the intended staggering, not evidence that the automations are currently active.
- **GitHub is shared memory.** Every run reads latest `main`, this role contract, [WORK_PRIORITY](WORK_PRIORITY.md), and the relevant owned issue/PR/branch. Do not depend on prior conversation context, stale run summaries or pinned historical PR numbers.
- **Authority:** approved [OVERALL PLAN](../../OVERALL_PLAN.md) defines WHAT; current approved [PROCESS](../../PROCESS.md) and [gate contracts](../gates/README.md) govern HOW and acceptance. Agents cannot relax gates, invent source facts or turn diagnostics into certified checkpoints. Neither this file nor a task prompt overrides them.
- **Continue, don't restart:** an owned issue/branch/PR is the durable handoff between runs. Continue the same unfinished work until delivered, demonstrably unworkable or explicitly reassigned. A change in assignment requires a reason and handoff; do not edit another agent's active branch.
- **Deliver code, not activity:** shortest real source-backed RED reproduction → production GREEN change → relevant regression(s). Refactor only when useful. P1–P7.5 are **expensive on-demand production acceptance tests, not routine unit tests**: run each once to earn PASS, persist at least PASS+timestamp, and rerun only when a material change invalidates that gate. Never require duplicate acceptance evidence bundles, a gate-only simulator or repeated 30/300-s, 100-mob or stochastic holdout jobs for unchanged behavior. Ordinary focused regressions remain appropriate. A reviewed production-code improvement may merge before the affected gate's full PASS; an unpassed gate is not a delivery veto. The Work1+Work2 common rule below defines the handoff.
- **Incremental gate progress / Pareto effort estimate:** split unfinished gates into existing testable production behaviors **without changing the priority order**. For a defensible comparable count, report measured `passed/known applicable` and coverage `c`, plus a **separate heuristic estimate of work completed** `E=0.25*c` for `c<=0.8`, else `E=0.2+4*(c-0.8)`. It encodes the illustrative assumption that the first 80% of cases cost 20% of effort and the final 20% cost 80%; it is **not observed engineer-hours, acceptance or a scheduling signal**. Mark both figures provisional with unknown source scope. Do not apply the curve to heterogeneous/small gate steps or invent a denominator. Keep the shortest critical path and unchanged issue ownership; report actual RED→GREEN fixes even when percentages do not move. No shadow KPIs or PR #60 diagnostic tick chasing.
- **Autonomy:** make ordinary technical decisions, fix manageable failures, commit/push/open PRs and safely merge within role without requesting constant approval. Ask only when genuinely blocked by external authority/permissions or a change to approved scope.
- **Reports:** one short factual result: behavioral/structural change, commit or PR, actual validation, and the next technical blocker. No forced '+1' metrics, shadow registers, mandatory inventory reports or timestamp-only commits. Notify the owner when the certified checkpoint count first changes from zero to one, not on every unchanged 0/148 run.

### Mandatory PR-to-gate verification on every Merge cycle

For **every newly integrated production-code PR**, Merge reads the PR's `M1 affected gates:` line, performs a quick sanity check against the real diff and deduplicates the applicable **checkpoint × gate pairs**. Merge does **not** manually grade the resulting test evidence or update numbers; the production script owns PASS/FAIL/PARTIAL and M1 bookkeeping. For each affected pair, choose and report exactly one outcome:

1. **Changed executable gate:** launch `/m1-run` with the enumerated gate arguments after the PR is merged. Actions runs actual selected-production code; `wf_gate.py` returns PASS/FAIL/BLOCKED and `m1_progress.py` updates the sole TSV with real qualifying PASS/PARTIAL, then recomputes totals. No Merge-side manual scoring, adjudication loop or ledger PR.
2. **Previously certified unchanged gate:** no rerun and no status mutation; only a proven material incompatibility invalidates accepted evidence.
3. **No new executable behavior:** no dispatch. Missing runtime, unexecuted inventory, sample count, slot visitation and bad denominators are rejected by the script, not translated into made-up percentages by an agent.

**Merging code and examining its reported gates are a single integration responsibility.** A safe, tested incremental improvement toward an approved gate is **mergeable even if that gate remains FAIL/BLOCKED**; neither full PASS nor a guaranteed numerical M1 increase is a merge prerequisite. After merge, inspect and target the changed gate from the PR's `M1 affected gates:` handoff and dispatch the affordable real production test. The authorized runner writes a defensible PASS/PARTIAL (including P7 coupled live DPS / required DPS), or leaves M1 unchanged when evidence is still insufficient. Do not replace this with manual grading, a mandatory full-gate retry, or “M1 unchanged” without examining the available cheap probe. A bounded native/2D probe is not a P7 PASS; stochastic sample count is not a coverage denominator. Never run unrelated heavy acceptance every hour.

**Merge-triggered GitHub Actions recorder (batch, direct main):** [`m1-on-demand-record.yml`](../../.github/workflows/m1-on-demand-record.yml) uses the EXISTING production `wf_gate.py --record-progress` and `m1_progress.py`. At the **end of each Merge cycle containing relevant merged PRs**, collect the actually affected `class:level:spec:gate` pairs from their PR descriptions **and real diffs**, deduplicate them, then post **one single-line command on the most recently merged PR**, for example:

```text
/m1-run druid:60:balance:P2 druid:60:balance:P3
```

The owner-authenticated comment on an **already merged PR to main** launches a single GitHub Actions run against **fresh main** for up to twelve explicitly named gates. Work agents provide the arguments in their PR descriptions; Merge is only the launcher and safety/diff checker. No scan of unchanged gates, no hourly CI polling. P5's current short production probe is allowed without `--heavy` and capped at 20 seconds to obtain an early genuine PARTIAL; a future full P5 300-second acceptance must use explicit `--heavy`. P6/P7 full acceptance similarly requires `/m1-run --heavy ...` and is never launched by default. An optional manual Actions dispatch exists if a merged PR comment is unavailable.

The live runner stores qualifying **PASS or FAIL/PARTIAL directly in the sole TSV**, even when a gate remains FAIL; BLOCKED, bogus denominators and nonexecuted probes never count. After the batch, the workflow recomputes the existing M1 scoreboard and, **only when the TSV changed**, writes that single file directly to `main` via the GitHub Contents API with a matching-blob-SHA concurrency check. No secondary JSON register, no separate M1 bookkeeping PR and no authored total counts. A rejected concurrent update must be retried with fresh main; never overwrite another writer.

**Script is the scoring authority.** Merge only picks the PR-declared applicable gate tokens and launches Actions after merge; it does not interpret each result, manually update percentages, or create a ledger PR. The executed `wf_gate.py` returns PASS/FAIL/BLOCKED plus measured numbers, `m1_progress.py` retains only defensible PARTIAL/PASS and computes the scoreboard, and Actions writes a changed TSV directly to main. The gate's own FAIL/partial output is useful even when the workflow exits successfully. Merge only checks that the workflow ran or reports an execution/permissions failure; no additional review hoop for a first positive PARTIAL. A recorded historical PARTIAL is a monotonic best-observed diagnostic, not a substitute for a newly regressed live test (regression stays visible in run output).
