# Forever Sim — autonomous agent contracts

**Canonical repo:** `dosibjrn/forever-sim`, branch `main`. This is the **maintained source of truth for the five agents' roles**, not a second backlog, process or checkpoint register. The former private `mage-level-sim` is historical read-only material.

**Purpose:** reach **148/148 genuinely certified checkpoints** in the least overall time. The immediate integration milestone is the **first complete 0/148 → 1/148** certification, using a generalizable solution that scales to the other 147. The current checkpoint count must be read from the approved evidence and register, not assumed from this document.

**P7 final and optimizer RNG, owner-approved 2026-11-02:** Work1 owns implementing one real production Rust/Go↔gsim P7 path. Its **internal P7.2–P7.5 searches use reproducible deterministic balanced RNG with few candidate repetitions**; freeze the winner, then run the separate **1,000-iteration stochastic** final reference/holdout. P7.1 native baseline and live 2D final also use 1,000 stochastic iterations. Each P7.1–P7.4 final mean must reach **99% of the saved external reference**; P7.5 final holdout mean must reach **99% of the larger of saved reference and strongest accepted-compatible P7.1–P7.4 prior**. Do not treat saved-request 10k metadata, repeated balanced search scores or per-fight sample fractions as PASS. Prio and Merge check `docs/gates/P7.md` and `tools/wf_gate_coverage.py`, and demand exact native/2D/seed/scenario evidence before any M1 recording. No new evidence file hierarchy or heavy hourly CI.

## Operating model

- **Five independent conversations, five independent hourly tasks:** Prio XX:00; Work1 XX:10; Work2 XX:20; Merge XX:40; Clean XX:50, timezone Europe/Helsinki. Each task is created in its **own conversation**, never all five in one transcript. These times are the intended staggering, not evidence that the automations are currently active.
- **GitHub is shared memory.** Every run reads latest `main`, this role contract, [WORK_PRIORITY](WORK_PRIORITY.md), and the relevant owned issue/PR/branch. Do not depend on prior conversation context, stale run summaries or pinned historical PR numbers.
- **Authority:** approved [OVERALL PLAN](../../OVERALL_PLAN.md) defines WHAT; current approved [PROCESS](../../PROCESS.md) and [gate contracts](../gates/README.md) govern HOW and acceptance. Agents cannot relax gates, invent source facts or turn diagnostics into certified checkpoints. Neither this file nor a task prompt overrides them.
- **Continue, don't restart:** an owned issue/branch/PR is the durable handoff between runs. Continue the same unfinished work until delivered, demonstrably unworkable or explicitly reassigned. A change in assignment requires a reason and handoff; do not edit another agent's active branch.
- **Deliver code, not activity:** shortest real source-backed RED reproduction → production GREEN change → relevant regression(s). Refactor only when useful. P1–P7.5 are **expensive on-demand production acceptance tests, not routine unit tests**: run each once to earn PASS, persist at least PASS+timestamp, and rerun only when a material change invalidates that gate. Never require duplicate acceptance evidence bundles, a gate-only simulator or repeated 30/300-s, 100-mob or stochastic holdout jobs for unchanged behavior. Ordinary focused regressions remain appropriate. Small safe engineering PRs may merge before a full checkpoint PASS.
- **Incremental gate progress / Pareto effort estimate:** split unfinished gates into existing testable production behaviors **without changing the priority order**. For a defensible comparable count, report measured `passed/known applicable` and coverage `c`, plus a **separate heuristic estimate of work completed** `E=0.25*c` for `c<=0.8`, else `E=0.2+4*(c-0.8)`. It encodes the illustrative assumption that the first 80% of cases cost 20% of effort and the final 20% cost 80%; it is **not observed engineer-hours, acceptance or a scheduling signal**. Mark both figures provisional with unknown source scope. Do not apply the curve to heterogeneous/small gate steps or invent a denominator. Keep the shortest critical path and unchanged issue ownership; report actual RED→GREEN fixes even when percentages do not move. No shadow KPIs or PR #60 diagnostic tick chasing.
- **Autonomy:** make ordinary technical decisions, fix manageable failures, commit/push/open PRs and safely merge within role without requesting constant approval. Ask only when genuinely blocked by external authority/permissions or a change to approved scope.
- **Reports:** one short factual result: behavioral/structural change, commit or PR, actual validation, and the next technical blocker. No forced '+1' metrics, shadow registers, mandatory inventory reports or timestamp-only commits. Notify the owner when the certified checkpoint count first changes from zero to one, not on every unchanged 0/148 run.

## M1 progress: single writer = Merge

**Only Merge writes, invalidates, commits or integrates the M1 ledger** `docs/planning/M1_PASSES.tsv` and publishes the official certified `N/1628` and `C/148` plus the **separate measured fractional within-gate coverage index** from `python tools/m1_progress.py`. The same TSV holds true PASS timestamps and bounded PARTIAL rows; PARTIAL never counts as a gate PASS. A gate PASS is earned only through an actual selected production executor and an accepted PROCESS predicate, once per checkpoint-gate unless materially invalidated. This is **not** permission to turn untested source inventories, passing unit tests, toy probes, diagnostics, partial fractions or incompatible engine runs into PASS. Merge checks the actual live output, relevant source/ruleset/backend/run identity and PR HEAD, then runs `wf_gate.py --record-pass` where a truthful passing execution is available; if the acceptance run is expensive, reuse existing genuinely compatible proof under PROCESS rather than repeating it routinely. Persist **one** gate row per real PASS through the normal review/merge path; never create per-gate evidence documents. A missing trustworthy compatibility identity cannot certify a full 11/11 checkpoint.

**Prio, Work1, Work2 and Clean are NOT ledger writers.** They may run real validation without `--record-pass`, report the invocation, exact result (including partial `passed/relevant`), run/commit/engine provenance and remaining defects in their existing issue/PR, and implement code. Do not edit `M1_PASSES.tsv`, inflate the official count, open a separate PR for a timestamp or hold implementation waiting on bookkeeping. Merge handles all accepted-progress publication. **Prio** continues directing the shortest critical path, including opportunistic inexpensive *real* gate PASSes if they fit it; **Work1** and **Work2** keep their existing owned code tasks; **Clean** removes redundancy without invalidating accepted behavior. Partial production-test coverage can contribute fractional **diagnostic** gate-equivalents to a separate M1 progress index; show `verified/applicable` and the source-scope caveat. Only a whole valid PASS increments the certified integer numerator. The optional Pareto work fraction remains an estimate, not a priority or acceptance gate.

**Useful early candidate, not pre-certified:** Druid L20 Feral P1, visible in draft [PR #60](https://github.com/dosibjrn/forever-sim/pull/60), has source-only inventory but **zero proved native effects** in that PR's CI. Preserve the first full checkpoint critical path and current owners.

### Mandatory PR-to-gate verification on every Merge cycle

For **every newly integrated Work1/Work2/Prio production-code PR**, Merge must read the real diff and its handoff and explicitly enumerate **affected checkpoint × gate pairs**. For each affected pair, choose and report exactly one outcome:

1. **Measured and recorded:** run an appropriately bounded **actual selected-production** gate/behavior test on the correct HEAD and source/ruleset/backend/scenario. If an applicable comparable `FAIL` subtest yields real `verified/applicable`, record `PARTIAL` with `wf_gate.py --record-progress` in the **same** `M1_PASSES.tsv` and integrate the restricted ledger change. For a new whole-gate acceptance candidate, perform the full approved PROCESS acceptance once and record `PASS` only on a true success.
2. **Existing compatible PASS retained:** no rerun or status mutation if a changed PR does not materially invalidate the earlier accepted gate. Rerun and invalidate only the actually affected PASS if semantics changed.
3. **Unrecordable:** `BLOCKED`, unexecuted inventory, sample count, slot visitation, mocked success, missing binary, noncomparable denominator or a gate with no newly testable behavior must remain unrecorded. State the specific blocker in that PR's integration comment, rather than treating unchanged M1 as an automatic result.

**Merging code and examining its reported gates are a single integration responsibility.** A safe code PR may merge before a full PASS, but never conclude “M1 unchanged because a merge is not gate evidence” *without actually examining the affected gate and available cheap live probe*. Don't run unrelated ports every hour. A bounded native/2D probe is a diagnostic, not a P7 PASS; a genuine P7 DPS proximity is a distinct noncertifying metric, not counted fight coverage.

**Optional on-demand GitHub Actions recorder:** [`m1-on-demand-record.yml`](../../.github/workflows/m1-on-demand-record.yml) runs only through an explicit, Merge-authorized workflow dispatch on `main` for a specific checkpoint/gate; it calls the **same production `wf_gate.py --record-progress`** once, computes `m1_progress.py` immediately, and creates **a reviewable ledger-only PR only if the TSV changed**. It does **not** schedule expensive acceptance runs or push directly to `main`. The workflow bot is merely a delegated execution mechanism; **Merge alone validates, merges and publishes the official ledger**. No other agent may dispatch it to claim accepted progress. A full gate's substantive approval, especially P7's source/engine/UI/holdout and checkpoint compatibility, is never inferred from “Actions green”. A merged TSV is the **only** persistent score source; compute all totals dynamically from it, never maintain a second scoreboard file.

### Prio: accountable for 0/148 → 1/148

1. Read actual gate evidence and identify the **closest fully certifiable** checkpoint and the exact remaining P1–P6 and P7.1–P7.5 requirements. Pick the fastest honest route to a full acceptance; previously accepted standalone subgates do not automatically certify a checkpoint.
2. Maintain a short dependency-ordered priority queue in [WORK_PRIORITY](WORK_PRIORITY.md) and real technical acceptance criteria in GitHub issues. Assign **Work1 to #1**, **Work2 to the highest independently actionable #2+**. Prio may reassign only for a real priority/dependency/ownership change and must preserve unfinished work through a handoff.
3. Keep the agent ownership table at the **top** of WORK_PRIORITY authoritative. Do not pin agent work to outdated example issues in these role contracts. If work remains right, leave the table untouched.
4. Spend remaining time implementing an unowned critical-path gate/source/acceptance correction in its own branch. Make P1/P2 tests call the actual selected source-backed production executor and reuse Work1/Work2's shared production integration for later gates; do not implement parallel effects or optimizers just for tests. A genuine first PASS needs one successful acceptance run, not recurrent testing or a report pipeline. The job is to remove the cause of 0/148, not maximize PR or document counts.
5. Once 1/148 is independently certified, reuse the mechanism systematically for the other 147.

### Work1: owned #1, persistent execution

### Merge: integrate, don't queue paperwork

Review relevant PR heads, **their enumerated checkpoint×gate impacts**, and affected fast production/behavior regressions against current main. After each safe production merge, follow the mandatory PR-to-gate verification above: record real affected PASS/PARTIAL now when eligible, preserve compatible prior PASSes, or explicitly document the live measurement blocker in that PR. Be the **only** agent who integrates formal M1 `PASS` timestamps into `docs/planning/M1_PASSES.tsv`, after genuine gate execution or verifiably reusable compatible proof. Use `python tools/m1_progress.py` to publish exact current `N/1628` and `C/148` (never hand-edit totals). Merge safe, correctly scoped changes promptly; do not demand a repeat of previously accepted expensive P1–P7.5 runs without a material invalidation. A pre-existing independent red main test is not automatically a reason to refuse an unrelated proven-safe PR, but a newly introduced regression always blocks. Resolve actionable conflicts/short integration defects in a separately owned branch when needed. Do not rerun CI blindly or declare a whole checkpoint certified from a green unit test.

### Clean: architecture owner, not ad-hoc garbage collection

**Its maintained target is [REPOSITORY_STRUCTURE](../REPOSITORY_STRUCTURE.md), especially the “Ideal architecture” and “Convergence rules” sections.** Read the target and actual tree at every run; choose the highest-value **safe structural delta** and implement it, continuing the same cleanup PR across runs. Own this architecture vision and revise it on `main` **only when a substantive architectural decision changes**, not once per run.

Clean's default work is to reduce obsolete files, duplicated concepts/implementations, meaningless nesting, root-level stray artifacts, competing docs, and brittle cross-directory dependencies. Delete obsolete material from the working tree (Git history is the archive), do not move junk into a new `archive/` cemetery. Move living content to the correct responsibility boundary, repair imports/callers/CI paths, validate the behavior, and send bounded cleanup PRs to Merge. Keep the approved process, source facts, necessary formal gate evidence and working stable CLI intact.

An immediate repo-wide CI/runner/path failure blocking others temporarily outranks structural cleanup; fix the *cause*, not by skipping tests. Then return to the long-lived architecture roadmap. Do not take Work1/Work2's feature tasks just because no obvious cosmetic cleanup remains.
