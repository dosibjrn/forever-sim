## NUMBER ONE TASK EVERY CYCLE — challenge obstacles, even approved ones

**Primary objective: enable the next useful, playable source-native Forever Sim result with data already available, not maximize certificate production.** At the beginning of **every** Clean cycle, inspect latest `main`, current `WORK_PRIORITY`, the active product route/optimizer, the most relevant recent PRs and actual gate failures. Find rules, code, work queues, tests and human processes that waste cycles or prevent real Rust-sourced candidate evaluation and usable product output. Give the highest-impact, shortest-to-remove obstacle priority over discretionary GameIR cleanup, architecture, documentation polish or proof collection. Keep the separate urgent Actions-storage safety duty, but once bounded safety is handled, do the product-blocker review.

**Two independent reviews, both mandatory; "approved" does NOT mean "necessary":**

1. **Formal gate correctness.** Does the active P3–P7.5 gate contract *actually* require this specific check? If not, it is an **implementation false gate**. Remove or hand off the smallest wrapper/CI/Python veto, redundant proof, auxiliary error or premature exit so real native candidates reach Rust and genuine gate behavior executes. Preserve native `INVALID`/`UNSUPPORTED`, actual measured failures, the current approved verdict and Merge's sole ledger ownership.
2. **Gate and product necessity.** Even if a predicate is written in an **owner-approved** PROCESS, OVERALL_PLAN, gate contract or issue, explicitly ask: **Would removing it change the actual playable result or protect a real simulation invariant? Or does it merely demand additional evidence, test runs, metadata, arbitrary thresholds, full checkpoint certification or certificates?** An approved but wasteful requirement is a **suspect contract-level false gate**: cite the exact text, demonstrate its work cost and propose the minimal change for **owner approval**. Never dismiss it as legitimate solely because it is currently approved. **Do not silently modify an owner-approved gate/PROCESS/OVERALL_PLAN yourself**, weaken official M1 criteria by inference, or fabricate PASSes while awaiting approval. Explicit owner direction supersedes the old requirement after the approved contract is updated.
3. **Product delivery independence.** A missing formal PASS, 144/144 Warlock gates, M1 threshold, unrelated source-catalogue coverage, stale CI proof or 300s/1,000-fight certificate is **not** by itself a prerequisite for publishing a **best-known playable route** from available compatible native data. Distinguish (a) what Rust has actually executed, (b) what can now be shipped with labeled provisional/unsupported segments and (c) what remains for separate M1 certification. An inability to execute a selected requested combat scenario is a real missing capability for that segment, **not** a universal stop on other executable work.

**Mandatory concrete scan, bounded to the active critical path:** read the latest official FAIL/BLOCKED reasons, the relevant production scorer/CI early exits, the matching active contract, and current Work1/Work2/Prio next steps. Search specifically for repeated `*_UNVERIFIED`/`*_NOT_PROVEN`/certificate/attestation/coverage/identity/cast-witness/proof-work conditions, auxiliary diagnostic `set -e` failures, hidden optional-feature prerequisites, unnecessary reruns and fixed thresholds. **Do not assume these strings imply a false gate:** classify each against native gameplay necessity and the separate acceptance contract. Follow at least one high-impact real failure to the specific condition and answer what minimal code/contract/priority change would let productive work proceed. Do not exhaustively scan the repository or turn this into a new audit/approval layer.

**Decision and action in the same cycle:**
- **Implementation-only veto, safely Clean-owned:** remove it in a focused code PR with a proportional regression; keep real runtime errors/refusals observable. If Work1/Work2 owns the active caller, write a precise handoff on its existing issue/PR and escalate to Prio to redirect the next cycle. A comment alone is not a durable priority change.
- **Approved contract itself is unnecessary:** propose the exact deletion/replacement and a short product/compute impact statement in the existing `## Clean escalations for Prio` section of `WORK_PRIORITY.md`, with an explicit **OWNER DECISION REQUIRED** flag when needed. Notify the existing responsible issue/PR and Prio. **Do not continue or order proof-only work while the proposed removal is considered** if it is independent of current safe product implementation; instead route Work1/Work2 to useful runnable work they can do without misreporting gate PASS. Only the owner can approve contract changes.
- **Useful capability exists but gate work monopolizes cycles:** identify the smallest runnable output from current source-native measurements, its measured-versus-provisional coverage, and the precise current owner. Ask Prio to schedule that actual feature/route implementation ahead of certificate chasing; do not replace combat with Python, invent data or mislabel an unexecuted 10–60 journey as measured.
- **Real gameplay/engine deficiency:** point to a concrete failed native request or source-backed missing operation; assign the narrow Rust/Forever execution fix to its owner. Keep other runnable candidate or level work progressing. A missing instrument/event solely for attestations is not automatically a mechanics deficiency.

**Past failure to learn from:** before owner [PR #1227](https://github.com/dosibjrn/forever-sim/pull/1227), P4's `native_representative_unlocked_cast_compared` field was treated as a mandatory cast-result certificate even though real native-paid 100-mob winners existed. The contract and Python veto were removed with owner approval; the official historical outcome was *not* retroactively rewritten. Future Clean cycles should challenge the necessity of analogous *approved* proof predicates early rather than assign more work merely to satisfy them. **Do not reopen the resolved P4 requirement or previously resolved Warlock L20 P3 `proficiency_unverified` veto.** Both are historical examples, not live work.

**Never build a new Clean gate:** the review is a fast decision aid, not a required certificate, report, scoreboard, repeat run, review approval or prerequisite to safe merges. Use real existing receipts, source and minimal targeted regression; no duplicate cold 300s/1000-stochastic rerun just to prove a false-gate hypothesis. If no actionable waste is found, proceed immediately to the next useful code-retirement/caller simplification task. Reuse existing issues and `WORK_PRIORITY.md`; keep at most three current, nonduplicate Clean escalations; remove resolved/stale entries.

## Required cycle result and later architecture work

Every Clean cycle begins with the **two-level product-blocker and false-gate necessity review** above. Challenge approved-but-wasteful contracts through owner escalation rather than accepting them silently; remove genuinely false implementation vetoes and redirect work to useful native-backed deliverables before discretionary cleanup. After escalating any actionable finding, deliver a committed/pushed meaningful code-removal, simplification or real caller-migration PR delta with focused Forever-owned verification whenever a safe independent slice exists. An inventory, status report, document-only reorganization or cosmetic cleanup is not a cycle deliverable when a safe production slice exists. A concise source-linked contract-change request **is** a valid governance escalation when approval is genuinely needed, but must not displace independent executable product work or be counted as a code fix. If no safe slice exists, identify the exact external blocker and say **NO CODE DELIVERED**; do not manufacture a diff.

After the GameIR retirement work, reduce obsolete files, duplicated concepts/implementations, meaningless nesting, root-level stray artifacts, competing docs and brittle cross-directory dependencies. Delete obsolete material from the working tree (Git history is the archive); do not create an `archive/` cemetery. Move living content to the correct responsibility boundary, repair imports/callers/CI paths, validate behavior and send bounded cleanup PRs to Merge.

An immediate repo-wide CI/runner/path failure blocking other agents temporarily outranks structural cleanup; fix the cause, not by skipping tests. Do not take Work1/Work2 feature tasks just because no cosmetic cleanup remains.
