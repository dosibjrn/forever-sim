# WoW Forever — seven checkpoint gates and gate-level RED → GREEN → REFACTOR

**Policy updated 2026-10-15.** Applies to each of the **148 checkpoints**: 9 classes × 4 levels (20/30/40/60) unrestricted = 36; Druid 4 specs × 4 levels = 16; other eight classes × 3 specs × 4 levels = 96. **No eighth gate.** Gate-level TDD is how each existing gate is built and admitted, not an extra quality gate. Use the newest Library baseline; all reference data must be pinned and provenance retained. Source DB + ruleset + encounter + continuous-actor/recovery objective MUST match across comparisons. A Classic 955HP proxy may be valid for a diagnostic scenario but MUST NOT be labelled a sourced real Forever NPC.

## What GREEN means (not merely a green test counter)

| Gate | Decisive external acceptance witness |
| --- | --- |
| **P1 — Spells/actions** | All source-legal, level/rank/form/conditional abilities found and correctly admitted into canonical GameIR / optimizer; action coverage denominator, provenance, valid ranks/requirements and no silent exclusion. A source-indexed L0 row is **not** evidence that an impactful L2 runtime effect works. Missing executable mechanics capable of affecting the winner must block an unqualified optimum claim. |
| **P2 — Talents** | All source-legal reachable talent identities/ranks, tree prerequisites and point-budget combinations covered; legal optimizer talent allocations actually selected/evaluated and source-derived effects executed or explicitly marked as impactful L2 gaps. Do not call a tree-position count a complete effect simulator. Include standard 21 L30 points; optional legacy bonus +5 only if the checkpoint explicitly requests it. |
| **P3 — Gear + contextual Top 5** | Complete, proven source-legal class/level gear universe and constraints (slots, armor/weapon proficiency, unique, 1H+offhand vs 2H, source-effect semantics); source-linked **top 5 legal items for each fillable slot for the current best whole build**, build-context stat weights, per-stat contributions, uncertainty and actual causal 100-mob swaps for consequential/near-top alternatives. Critical nonlinearity cannot be disguised as linear weights. The current implementation uses raw-byte-attested class-filtered 1–255 item captures; this is the chosen proof technique for source completeness, not a separate P8. Unverified provisional catalogs remain diagnostics only. |
| **P4 — independent 30s search** | Independently discover a complete legal **gear × talents × APL/rotation × recovery** build without using the old/held-out winner as a seed. Real shared wall clock ≤30s (count source prepare, failures and screening), unique full-build identities, CPU/events/wall evidence, scored winner independently completed **100 consecutive mobs** with continuous actor, paid recovery, incoming survival and pinned encounter. Do not pass on 2/4/20-mob screening alone. |
| **P5 — independent 300s search** | Cold independent run under ≤300s on **the same objective and legal universe**; paid candidate coverage measured by unique legal full configurations, not cheap duplicate probes or test count. Current explicitly strengthened threshold: **N300 ≥ 10 × N30** and completed 100-mob finalist. Earlier six-gate historical contract required merely broader search; do not silently mix definitions in the scoreboard. Record any intentional run-frontier cap honestly; a 10× gain over a toy partial frontier is only diagnostic, not full checkpoint P5. |
| **P6 — 1% saturation** | Both independent winning configurations cold-replayed through the *same* canonical 100-mob CombatRuntime/objective, same source DB and source-qualified target, no comparator-seeding. `T30 <= 1.01*T300`, times measured in seconds/mob, complete kills and recovery. Same numerical result from two incompatible spatial scenarios is **not** a comparison. |
| **P7 — legacy hold-out** | Independently run the **old Decisions optimizer** to produce its actual best bounded complete gear+talents+rotation(+recovery) candidate; make that exact configuration an explicit legal candidate inside the *new* GameIR + CombatRuntime. Reevaluate it and the new winner on the **same source/context/objective** for 100 mobs; `Tnew <= Tlegacy + 1e-9 s/mob`. Do **not** compare native old scorer numbers to new scores. Old winner absent, item legality unproven, different 2D/pack/recovery rules, or no actionable legacy config => **BLOCKED**, not PASS. P7 does not override P1–P6. |

These criteria distinguish coverage and execution. L0 source presence is necessary but not by itself evidence of all L2 gameplay semantics. Unknown effects are explicit; do not silently zero unhandled source-legal contenders. Be honest about bounded search vs global optimum.

## Required cycle FOR EACH P1–P7 within each checkpoint

1. **RED — acceptance must fail first.** Run the *actual gate acceptance predicate* against current baseline; save a reproducer, input/context fingerprint, failed assertion, source provenance and log. Missing Forever data is a typed blocker with next actionable acquisition, never a fabricated null effect. Record `test_id`, `criterion_id` and evidence SHA256.
2. **GREEN — make the actual gate pass.** Implement the smallest **generic** source → IR → executor → optimizer correction; run the **same acceptance test ID and criterion** and save the semantic gate verifier's certificate. A green unit test, synthetic fixture, or narrowed candidate set alone is **not** gate GREEN. Record full benchmark/coverage for P3–P7.
3. **REFACTOR — mandatory genericity audit immediately after GREEN.** Inspect every new branch: did we add a `class == druid`, spell name, item ID, form/talent special case, hardcoded numeric mechanics, or a second search/recovery code path? For each such change either **GENERALIZED_ENGINE**, **MOVED_TO_SOURCE_DATA**, or **REMOVED_DUPLICATE** (with code + evidence). Distinct mechanics should be represented in common typed effect IR and source facts, not in a class-specific optimizer branch. No unresolved class-specific engine exceptions accepted. Check shared invariants and data provenance.
4. **POST-REFACTOR GREEN — re-run the SAME gate predicate**, its 100-mob result where relevant, all previously completed gates for that checkpoint and at least one appropriate **other class/level/spec/synthetic-IR context** regression. If the generalization changes scores, replay downstream gates; never reuse a stale certificate. Store evidence and SHA256. Only then mark cycle `COMPLETE`.
5. **PROMOTION** is by the external seven semantic gate verifiers **plus** seven finished cycles, on the same current source-version and objective. `RED`, `GREEN`, `REFACTOR`, and `COMPLETE` are workflow phases; they are **not** substitutes for actual P1–P7 PASS. Block on missing source, unreplayed changed baseline, unresolved effects, or unverifiable legacy. 0/148 remains the last published strict count unless an authoritative complete certificate proves otherwise.

## Required handover after EVERY W

Report checkpoint × gate state, one meaningful bottleneck removed, hard before/after empirical evidence, source revision, external gate validator outcome, RED/GREEN/REFACTOR evidence IDs, genericity finding, cross-class regression, remaining blockers and next critical gate. Do not create a release for report/test-count churn. Check the latest Library version before work and before publishing. Keep 30s screens, 300s work and 100-mob evaluation clearly distinct. A 10× partial-frontier benchmark does not certify full-world item coverage or P7 parity.

## Executable evidence contract

`src/game/checkpoint_gate_cycle.py` checks the formal RED/GREEN/REFACTOR evidence ledger for exactly these P1..P7, its source-context hash, stable criterion/test identity, independent post-refactor gate rerun, class-specific-change resolution and cross-context regression. `tools/wf403_gate_cycle_audit.py` audits such a ledger from JSON. **This is a workflow-evidence validator, not a fake gameplay verifier**: it always returns `checkpoint_accepted=false` and requires separate actual P1–P7 semantic certificates before accepting a checkpoint. Sample JSON ledger: `evidence/wf403/GATE_CYCLE_EXAMPLE.json` (demonstrates unfinished state, not a passing checkpoint).
