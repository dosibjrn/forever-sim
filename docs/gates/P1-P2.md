# P1–P2 — abilities and talents

These are the operative approved predicates: P1's v2.11 representation/selected-backend boundary is unchanged; P2's v2.17 scope is the observable mechanics relevant to the solo-leveling objective, with explicit treatment of genuinely non-applicable effects. Shared backend and source requirements are in [COMMON](COMMON.md).

### P1 — Legal abilities and ranks

Source-derived legal/conditional abilities at the checkpoint level, correct ranks and prerequisites, available to candidate generation **on the selected production executor**; explicitly report unresolved cases and meaningful inability to execute a relevant ability. When selected MythicSim Rust/Go executes the source-legal ability, **a second Python GameIR ActionDefinition or gsim combat wrapper is not required** for P1 effect evidence. Existing GameIR/gsim behavior tests remain valid for a selected gsim executor. Never silently prune a legal action based on class or supported-effect whitelist. Do not equate an L0 source label with correct native execution.


**Effect-test boundary (owner-approved 2026-11-01):** P1 validates **whether** the source-legal, scenario-relevant ability really changes state in the selected production engine; it does **not** prescribe **how** the ability is implemented. Derive the expected universe independently from source-backed class, level, rank, permitted talent/spec and scenario. Autoattack, pet action, passive/talent/rune and noncombat source entries require correct role classification rather than blanket missing-player-action failures. Explicit, scenario-scoped `DOES_NOT_AFFECT_SIM` decisions stay in a separate list and never count as an executed PASS. **No separate acquisition proof:** Forever must not demand trainer records, learned-spellbook certificates, source acquisition batch matches or quest completion to test P1. MythicSim's selected native prepare/simulation owns spell and rank validity; reject a concrete native INVALID or UNSUPPORTED response rather than inventing local acquisition evidence requirements. Execute the isolated native combat effect directly in real pinned MythicSim Rust/Go when possible; actual gsim 2D world integration is required only where the effect depends on world-owned geometry/movement/CC. A missing GameIR or gsim wrapper alone is NOT evidence that native MythicSim lacks an ability. Short paired controlled tests suffice; an APL-row removal which changes scheduling is only a diagnostic, not an isolated behavioral proof. Preserve actual optimizer candidate reachability as a separate P1 condition and reject non-executed, stubbed or synthetic effect evidence. See [P1 implementation guide](P1_VALIDATION.md).

**Observable P1 impact on selected backend (USER-REVISED 2026-10-26):** The canonical source-derived legal/conditional ability denominator remains unchanged. A source-legal, relevant ability must be usable by candidate generation and must show its applicable effect through the **real selected production executor** in an appropriate precondition/target/form/range/resource scenario. Evidence can be a target HP change, real DoT ticks, heal, stat/resource change, aura that actually influences a stat/action, CC-afflicted movement/behavior, interrupt, pushback, pet action, or analogous mechanical consequence. Mere registration, successful cast counter, effect metadata, synthetic stub event or inactive aura is NOT proof. Trigger conditional abilities in a suitable situation; if not actually tested, report a concrete unresolved condition, not a silent PASS. For a spell with multiple relevant independent effects, test its applicable effects without requiring one universal DPS delta. A deterministic paired positive/negative control or an equivalent targeted behavioral assertion is sufficient. Never demand a 100-mob run **per spell** as an additional P1 gate. Highest level-legal rank is sufficient where the pinned P1 scope excludes downranking; retain legal granted abilities. A reachable legal spell absent from gsim but present and behavior-tested in msim/hybrid is P1-covered on the msim path.

### P2 — Talent legality and effects (USER-REVISED 2026-11-02: OBJECTIVE-SCOPED, BINARY)

A talent rank has **exactly one acceptance state**: `PASS` or `FAIL`. The complete source-derived, structurally reachable rank set is the P2 denominator; do not silently exclude inconvenient ranks or actions. The P2 objective is the pinned **solo leveling simulation** (real elapsed time per mob/route, including combat, pull/movement, survival and paid recovery), not a complete implementation of all game modes. A non-DPS mechanic may be highly relevant; lack of a DPS delta is never sufficient to declare it irrelevant.

**Machine evidence contract:** every current P2 report must include `production_engine` with exactly one of `gsim`, `msim`, or `msim+gsim-world`. A Python GameIR-only run is diagnostic: it cannot satisfy P2 acceptance or contribute M1 partial coverage.

A reachable rank is **PASS** if and only if all of the following are true:

1. **Legal allocation works**: its point-budget, tier, prerequisites, form/level restrictions and rank application succeed using the canonical talent representation.
2. **Applicable effect executes, or explicit non-applicability is justified**: for every effect that can change the pinned solo objective, the described effect/unlock/condition has a real implementation through the selected production backend (`gsim`, `msim`, or the integrated `msim+gsim-world` path); it changes the applicable observable gameplay state/event/action availability. An effect whose necessary trigger/actor/target cannot occur in that pinned scenario may instead be classified `DOES_NOT_AFFECT_SIM` **with a concrete, source-backed, scenario-specific reason**. That classification is not a substitute for an unimplemented, hard-to-test or merely unselected mechanic. A placeholder or silent no-op for an applicable effect remains FAIL.
3. **Appropriate tests PASS**: for applicable effects, automated tests exercise the rank's actual gameplay effect/unlock through the production implementation with meaningful preconditions, expected outcomes and suitable negative controls. For a `DOES_NOT_AFFECT_SIM` effect, test the scenario exclusion/predicate or otherwise verify concretely from the pinned scenario and source that its trigger or affected entity cannot arise; no simulated effect, fictitious DPS delta or unrelated gameplay scenario is required. Use deterministic small paired tests where practical, not a 100-mob run for every rank. Do not treat a catalogue assertion, unsupported-effect flag or unverified claim of irrelevance as a passing test.
4. **Search can use it**: legal allocations are not filtered out of candidate generation, and newly unlocked actions are represented so P4/P5 can genuinely execute them.

If one condition is missing, **FAIL** with a *concrete actionable defect*: e.g. `IMPLEMENTATION_MISSING`, `BEHAVIOR_TEST_MISSING`, `BEHAVIOR_TEST_FAIL`, `ALLOCATION_INVALID`, `SEARCH_ACTION_MISSING`, or an unjustified non-applicability claim. Fix the defect and rerun. A rank with multiple effects needs appropriate implemented/tested behavior for each **applicable** effect and an explicit justified exclusion for any genuinely non-applicable effect; no independent provenance-essay or semantic-proof exercise. A fully excluded rank may still count as P2 PASS for legal allocation/search plus verified objective non-applicability; its excluded effects must not be reported as executed behavioral PASSes.

**Explicitly prohibited as acceptance states, blockers or W work items:** `PARTIAL_SEMANTICS`, `SEMANTICS_UNVERIFIED`, `SOURCE_BRIDGE_UNVERIFIED`, "prove semantic parity", a source-version provenance bridge pursued in isolation, source archaeology to reconfirm already implemented/tested behavior, or additional talent-semantic proof rounds. Record uncertainty as informational metadata if helpful; it is **not an eighth gate and is not an automatic P2 veto**. A known failed test or an actually missing/incorrect implementation remains a genuine FAIL. Do not invent unavailable game data, fabricate a passing test, or hide a known contradiction.

**P2 GREEN** when **every** reachable rank is PASS under the conditions above, including prerequisite/allocation tests and real executor integration; no separate semantic certification is required. Group tests by generic effect family, parameterize rank differences, and reuse one working executor. A fast representative 100-mob smoke can catch cross-cutting runtime regressions, but running 100 mobs for each rank and repeatedly re-proving source semantics is not required by P2.

**Migration of old P2 reports:** Historical `129/129 executors, 14 partial semantics, one source bridge` does not by itself say either PASS or FAIL under this contract. For each formerly flagged rank, examine **only whether its real implementation and behavioral tests already satisfy the above predicate**. If yes, mark PASS immediately. Otherwise add exactly the missing implementation/test/legality defect and fix it; **do not spawn a new semantic-verification task**. Recompute the real P2 status on the merged current code and continue downstream gates as soon as GREEN.


**Observable P2 impact on selected backend (USER-REVISED 2026-11-02):** For each source-legal, structurally reachable talent rank, check legal acquisition. For each **applicable** effect, check actual production behavior on `gsim` OR selected `msim-rust`/`msim-go` (live hybrid when world-dependent): compare the same legal setup **with versus without that rank** (or adjacent ranks and an explicit tested unlock/control), and assert at least one **causally appropriate** observable effect in the designed trigger scenario. For an explicitly non-applicable effect, verify its scenario exclusion instead of demanding an artificial effect demonstration. The effect may change damage/healing, stats, costs, cast/cooldown, CC/survival, pet mechanics, or grant a usable new ability. Do not require a nonzero DPS difference where none should occur. The rank must be usable by source-derived allocation and search; unlocked spells must be executable in P4/P5 as defined there. Source-field access, talent-tree label, Go implementation filename and `notSimulated=false` are NOT substitutes for an actual behavioral test; do not label ordinary source uncertainty as a new semantic-certification gate. No double implementation requirement across backends. A rank with a known no-op/placeholder for an **applicable** effect in its chosen executor is FAIL until a real implementation is used. P2 still keeps all reachable rank allocations and legal search candidates, including objective-neutral ranks.
